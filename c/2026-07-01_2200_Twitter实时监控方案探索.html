好问题，先做可行性分析。让我查一下我们的 Twitter 工具能力。

xurl CLI 能力概览：

| 操作 | 命令 | 说明 |
|------|------|------|
| 搜某人推文 | xurl search "from:handle" -n 10 | 拉取最近 N 条 |
| 读单条推文 | xurl read POST_ID | 获取全文 + 元数据 |
| 查用户信息 | xurl user @handle | 粉丝数、简介等 |
| 流式监听 | /2/tweets/search/stream | 近乎实时 |

已有基础设施： 飞书 Webhook 推送 ✅ | Hermes Cron 定时 ✅ | LLM 分析能力 ✅

两种方案对比：

| 维度 | 方案 A：轮询 | 方案 B：流式监听 |
|------|:-----------:|:---------------:|
| 时效性 | 5~10 分钟 | 秒级 |
| API 要求 | Basic（$100/月） | Pro/Enterprise（$5000+/月） |
| 复杂度 | 🟢 简单 cron | 🔴 常驻进程 + 断线重连 |
| 可靠性 | 🟢 稳定 | ⚠️ 需处理重连 |

LLM 分析能力： 每条新推文可自动生成：一句话摘要、情绪判断（积极/中性/负面）、关键主题标签、潜在影响评估、中文翻译。

建议先用方案 A 起步，每 10 分钟扫一次。

🤖 Hermes (22:05)
1 分钟级别可行，有两种路径：

路径 A：纯 Cron（简单粗暴）
每分钟一次 cron → xurl search → 对比 ID → 有新推文则分析推送。每天 1440 次 Agent 调用，约 $1~3/天的 LLM 成本。

路径 B：后台监听 + 按需分析（更经济）
后台进程每分钟轮询（无 LLM），发现新推文写入 trigger 文件 → 另一个 cron 检查 trigger 后调用 Agent 分析。只有新推文才消耗 LLM token，一天假设 20 条推文，成本极低。

共同前提：xurl 已安装 + OAuth 认证 | X API 套餐 ≥ Basic（$100/月）| 搜索接口限速 450 次/15min 完全够。

Free 套餐下可行的路：

| 方案 | 可行性 | 风险 |
|------|:---:|------|
| 浏览器抓取 | ✅ | 需登录态 + 反爬风控 + 可能封号 |
| Nitter RSS 中转 | ❌ | 绝大多数实例已被 X 封杀 |
| 第三方服务（IFTTT/Zapier/RSS.app） | ⚠️ | 大部分已死或极度不稳定 |

现实结论：1 分钟 + 免费 = 浏览器抓取，没有优雅方案。

三条路：
1. 接受 5~10 分钟延迟 → 也要 Basic，一样要 $100
2. 坚持 1 分钟 → 浏览器抓取（有风险）
3. 升 Basic → 正规军

第三方服务的现实很残酷：

| 服务 | 还能用吗 | 问题 |
|------|:---:|------|
| IFTTT | ⚠️ | X 集成去年大批下架 |
| Zapier | ⚠️ | 同样受 API 限制，免费层 100 次/月 |
| RSS.app | ❌ | 砍了 X 免费支持 |
| RSSHub | ⚠️ | 自部署需要反爬手段 |

外部免费的 X 监控服务基本死光了。

但有一个曲线救国的路子——用 Hermes 自己做"第三方服务"：

``
Hermes Cron（no_agent 模式）
每分钟跑 Python 脚本 → curl x.com/某人 → 提取最新推文 ID
对比上次 ID → 有新则写 JSON trigger

Hermes Cron（Agent 模式）
每分钟检查 trigger → 有则 LLM 分析 → 飞书推送
无则静默退出（零 token）
``

成本几乎为零，延迟 ~1 分钟，每分钟 1 次请求跟普通刷网页没区别。
